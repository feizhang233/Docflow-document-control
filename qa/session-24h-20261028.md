# Persistent session browser verification — 2026-10-28

Verified against [the local Documents preview](http://127.0.0.1:5173/documents/all), using Google Chrome, the Vite frontend and FastAPI backend, an isolated temporary SQLite database and disposable test accounts. No production accounts, records or services were accessed.

Migration `20261028_30` applied successfully over `20261028_29`, preserving the existing column visibility/order preferences. Browser verification included the final backend refresh-overlap fix and frontend shared session recovery.

For deterministic expired-access testing, a temporary launcher outside the repository called the application's original access-token function and shortened only the returned access JWT expiry to five seconds. The original session ID, account/version claims, refresh token, cookie lifetime and absolute session deadline were preserved. The launcher was removed from the running setup after these tests: the review API now uses normal 30-minute access tokens and a 24-hour session setting.

| Check | Result |
| --- | --- |
| Existing saved sign-in | The previously signed-in disposable account opened the register without a login form after migration. |
| Fresh login | Administrator signed in normally; its prior Document Type-first custom order remained intact. |
| Reload | Reloading the page with expired five-second access recovered automatically without a login form. |
| New tab | A second local register tab restored sign-in without credentials. |
| Close and reopen page | Closing that tab and opening the register again restored the saved sign-in. |
| Concurrent expired-access requests | Documents → Settings produced simultaneous 401 responses for projects, columns and workflow. Exactly one refresh request succeeded; all three protected requests then succeeded on retry. |
| Absolute deadline preserved | The same database session record retained the identical original expiry before and after successful recovery. Refresh did not move the deadline forward. |
| Explicit logout | Signing out in one tab immediately signed out the other tab. Reload remained on the login page and did not silently recover the previous session. |
| Same-role account switch | Signing into a second Administrator updated the other open tab's identity and loaded that account's separate Document Title-first preference. |
| Temporary API failure during startup | A fresh page displayed only “Could not restore your session” and Try again. It contained zero private tables/account controls and no login form; saved sign-in was not cleared. |
| Recovery after temporary failure | Once the API was restored, Try again recovered the same account without credentials. |
| Expired session boundary | Only the disposable second account's stored session expiry was moved into the past. Reload then required sign-in and showed zero private tables, even though the access token had been issued by the normal configuration. |
| Final normal configuration | A fresh login to the original Administrator succeeded after restoring normal access-token lifetime; its saved columns were still present. |

The concurrent-recovery access-log sequence was:

```text
GET /api/settings/projects → 401
GET /api/settings/columns → 401
GET /api/settings/workflow → 401
GET /api/auth/me → 401
POST /api/auth/refresh → 200
GET /api/settings/columns → 200
GET /api/settings/projects → 200
GET /api/settings/workflow → 200
```

Screenshots were inspected for the unavailable-session state and restored authenticated register. The local normal-configuration API and frontend were left running for review. This is not a production deployment.

Limits: the browser pass did not wait 24 hours or restart the user's entire browser application. Exact 24-hour boundaries and refresh-overlap cases are exercised by the backend time-based regression tests; this pass used shortened access expiry and an isolated stored-expiry simulation. Other browser engines, physical devices and a complete screen-reader audit were not exercised.
